# Scoring correctness

The scoring pipeline (invert RoPE → invert WHT → combine with calibrated query statistics → aggregate over offsets) is the arithmetic that decides which KV keys get evicted. This page decides three hypotheses earlier waves left open. All three concern the **pre-rotation and aggregation stages**, not the WHT itself ([[walsh-hadamard-transform]], [[ta-1-wht-inversion-256]]).

## Bottom line

| Hyp | Question | Verdict |
| :-- | :--- | :--- |
| **H1** | Is `n_offsets == 0` reachable via the documented CLI, and does the default `mean` aggregate then emit NaN? | **CONFIRMED** — reachable by plain defaults; `mean` yields NaN on both the CPU and GPU paths; `max` yields a constant degenerate tie. |
| **H2** | Does the scorer's RoPE inverse match the target model's MRoPE? | **CONFIRMED defect** — the scorer treats all 256 head dims as two rotary halves with pairs `(f, f+128)` and `ω_f = θ^(−2f/256)`, while qwen35 rotates only 64 dims under MRoPE sections; the inverse is not an inverse of the model's forward rotation. |
| **H3** | Is `freq_scale_sq` really always 1.0? | **Dead code (b)** — `cos²(ω·0)+sin²(ω·0) ≡ 1` by construction; the paper's `fscale²_f = 1/ω²` appears nowhere in `src/`. Not intentionally disabled (no flag), not active elsewhere. |

Two of these are **new, unlisted defects**, and each deserves its own issue page:

- **H1 is the worst of the three.** Under plain defaults (`src/common/common.h:755` → `offset_max = 0`; `:758` → `agg = mean`) the CPU path computes `0.0f · (1.0f/0.0f) = NaN` (`src/src/llama-triattention.cpp:450`, `:501-503`) and the GPU path computes `0.0f/0.0f = NaN` (`triattention-score.cu:296`) for **every candidate key**. Both launch scripts omit `--triattention-offset-max` and `--triattention-agg`, so the shipped workflow runs exactly this configuration. The NaNs then reach the selector's `std::partial_sort` comparator `scores[a] > scores[b]` (`llama-triattention.cpp:867-870`), which is not a strict weak ordering over NaN ⇒ undefined selection (`[INFERENCE]` — standard-library contract, not read from a file). This belongs with [[ta-7-config-validation]] in spirit but is a distinct runtime failure, and it warrants its own issue page.
- **H2 is the second new defect.** It is stronger than [[triattention-calibrate]]'s open "pre/post-RoPE capture" question: even a pre-RoPE capture would not fix it, because the scorer takes no `n_rot`, no `sections`, and a single `positions[]` array — it cannot represent a partial/MRoPE basis at all.

**What this means for the roadmap.** All three verdicts sit on the eviction-quality track of [[roadmap]] — item 1 (port the [[ta-1-wht-inversion-256]] fix) and item 4 (dynamic `min_history_budget`, [[ta-2-budget-starvation]]) — because each changes what "eviction quality" means before either item can be measured.

- **H1** touches **item 4** directly: eviction that runs on NaN scores is meaningless in exactly the long-prompt regime item 4 governs. It also taints **item 1**, since any eviction-quality benchmark against this build measures the NaN/constant path, not real scoring.
- **H2** touches **items 1 and 4** (a second, independent reason eviction quality cannot be trusted) and **item 6**'s premise: the scorer inverts around a wrong RoPE next to the wrong WHT ([[walsh-hadamard-transform]]).
- **H3** resolves the already-filed candidate [[ta-5-freq-scale-dead-code]] from "either dead code or disabled" to "provably dead code". It is not on the six-item list, but it biases every measurement of items 1 and 4, because the shipped scoring is not the formula the paper commits to.

## Evidence

### H1 — `n_offsets == 0` is reachable, and the default `mean` aggregate really emits NaN

**Reachability, with no guard on any hop.** The default is `int32_t triattention_offset_max = 0` (`src/common/common.h:755`); `--triattention-offset-max` registers with that value and never overrides it (`src/common/arg.cpp:4714-4720`). The value travels unchanged: `common_init_result` forwards `params.triattention_offset_max` (`src/common/common.cpp:1409`) into `llama_triattention_init`, which does `cfg.offset_max = (uint32_t)offset_max` with **no validation** (`src/src/llama-context.cpp:4358-4394`). `triattention_build_offsets` returns zero elements for 0, since its loop starts at `d = 1 ≤ offset_max` (`llama-triattention.cpp:333-339`), so `state->n_offsets = triattention_build_offsets(state->offsets, cfg->offset_max)` is 0 (`:683-684`) — again with no `n_offsets == 0` guard (a grep for `n_offsets` across the file finds only its definition, uses, and log line). Two artifacts disagree with the code default: the struct comment "default: 65536" (`llama-triattention.h:133`) and the design document's 65536 (`src/docs/TRIATTENTION.md:84`) — further evidence that the zero case is unintended and unannounced. `scripts/start_server_turbo.sh:35` and `scripts/run_cli.sh:24` pass `--triattention-stats`, `--triattention-budget`, `--triattention-window`, `--triattention-protect-prefill` and **never** `--triattention-offset-max` or `--triattention-agg`. The documented CLI and both launch scripts therefore reproduce the zero case verbatim.

**NaN for the default aggregate (`mean`).** In `triattention_score_keys`, `inv_n_offsets = 1.0f/(float)n_offsets` (`llama-triattention.cpp:450`) and `total_score` is initialised to `0.0f` (`:462`); the offset loop (`:465-499`) never executes, and for `TRIATTENTION_AGG_MEAN` the code then does `total_score *= inv_n_offsets` (`:501-503`) ⇒ `0.0f · (1.0f/0.0f = +inf) = NaN` under IEEE-754. The GPU kernel's mean branch is `total_score = sum / (float)n_offsets = 0.0f/0.0f = NaN` (`triattention-score.cu:291-296`). Which path runs does not matter to the verdict: `triattention_init_gpu` is attempted unconditionally on every prune and only falls back to CPU on failure (`llama-triattention.cpp:1162-1166`, `:885-916`). `mean` is the documented default: `src/docs/TRIATTENTION.md:87`; `triattention_agg = 0` (`common.h:758`); `TRIATTENTION_AGG_MEAN = 0` marked "Paper default" (`llama-triattention.h:88`). `[INFERENCE]` — the float arithmetic is read from the source, not observed in a run; the GPU expression is unambiguous because its numerator is a literal 0 regardless of `-ffast-math`.

**The `max` aggregate is not NaN, but is degenerate.** With zero offsets the CPU max branch never fires either, so `total_score` remains its `0.0f` initialiser and every key scores exactly 0; the GPU max branch leaves `max_score = -1e30f` (`triattention-score.cu:280-287`), so every key scores exactly −1e30. Exact ties ⇒ arbitrary eviction. A secondary hazard on the same input: `cudaMalloc(&state->d_offsets, config->n_offsets * sizeof(float))` requests **zero bytes** (`triattention-score.cu:439`); if the runtime rejects a 0-size allocation, `CUDA_CHECK` fails and the scorer silently falls back to the CPU path with the same NaN outcome. `[UNVERIFIED]` — 0-size `cudaMalloc` behaviour was not exercised on this machine.

### H2 — the scorer's RoPE inverse is not an inverse of the model's MRoPE (CONFIRMED defect)

**The model rotates 64 of 256 dims, under MRoPE.** `build_layer_attn` feeds both `Qcur` and `Kcur` to `ggml_rope_multi(ctx0, ..., n_rot, sections, rope_type, ...)` (`src/src/models/qwen35.cpp:368-377`, again at `:714-719`). `n_rot` is the graph member `hparams.n_rot()` (`src/src/llama-model.h:862`), loaded from `LLM_KV_ROPE_DIMENSION_COUNT` (`src/src/llama-model.cpp:1486`); `sections` is loaded from the GGUF's `LLM_KV_ROPE_DIMENSION_SECTIONS` (`qwen35.cpp:6`, copied at `:168-169`). The upstream contract for a partial rotation is explicit: "pass `n_dims` smaller than the head size to `ggml_rope_ext`. Dims from `n_dims` to the end are copied as-is" (`src/docs/development/HOWTO-add-model.md:169-172`). For the target model, `qwen35.rope.dimension_count = 64` and sections `[11,11,10,0]` (sum 32 = 64/2, i.e. 64 rotated dims in half layout), so dims 64…255 are never rotated and the true frequency exponent is `ω_f = θ^(−2f/64)`. The 64 and the sections come from [[ternary-bonsai-2-27b]]; `[UNVERIFIED]` — the GGUF metadata was not read on this machine.

**The scorer inverts a 256-dim, full-head rotation.** `triattention_build_omega` uses `exponent = −2f/head_dim` over `freq_count = head_dim/2 = 128` (formula at `llama-triattention.cpp:309-312`, called with `fc`/`head_dim` at `:676-677`), i.e. `ω_f = θ^(−2f/256)`. `triattention_invert_rope` then rotates **every** pair `(f, f + freq_count) = (f, f+128)` across all 256 dims (`:382`; the signature takes `head_dim` and `freq_count` and has no `n_rot` and no `sections`), and the CUDA kernel does the same with `freq_count` threads per cell pairing `f` with `f + freq_count` (`triattention-score.cu:9-10`, `:230-260`). `gcfg.freq_count = cal->freq_count` and `gcfg.head_dim = cal->head_dim` propagate the same numbers to the GPU (`llama-triattention.cpp:895-897`). The scorer's public signature likewise carries a single `positions[]` and no section array (`llama-triattention.h:270-294`).

**Why this is (a) a real defect and not (b) compensated or (c) harmless.** The recovered "pre-RoPE" K is not the model's pre-RoPE K: for `f ∈ [0,32)` the real slot is a genuinely rotated dim but its paired imaginary slot `f+128` was never rotated, and for `f ∈ [32,128)` both slots are never-rotated dims to which the code nevertheless applies a rotation. The angle is also wrong at the right frequency: the code's exponent differs from the model's by a factor `θ^(2f(1/64 − 1/256)) = θ^(3f/128)`, so the `cos(ω_f·δ)` term advances at the wrong rate in `δ` — which is precisely the "distance horizon" the geometric offsets exist to probe.

- **(b) compensation:** none found. `src/src/turbo-rotation-data.h` (grepped, never read in full) contains no `omega`, `freq_count`, `head_dim` or `ROPE` symbol — it cannot supply a frequency table — so `omega` comes solely from `triattention_build_omega`. The calibration tool uses the same `head_dim/2` half-layout pairing ([[triattention-calibrate]]), but that does not cancel: it measures **post-RoPE** q, which the scorer leaves untouched while it applies a non-matching rotation to k, so the two errors compound into a phase `φ_f` that corresponds to no basis in the model.
- **(c) "only needs a basis":** refuted. A basis change must be the *same* linear map on both operands; here the query side is unrotated and the key side receives a map that is not the model's forward rotation ([[ta-1-wht-inversion-256]] is the analogous, separate failure on the WHT half of the same pipeline).

### H3 — `freq_scale_sq` is provably 1.0: dead code, not a disabled feature (verdict b)

`triattention_build_freq_scale_sq` computes `c = cosf(ω[f]·0.0f)`, `s = sinf(ω[f]·0.0f)`, `freq_scale_sq[f] = c*c + s*s` (`llama-triattention.cpp:320-327`). At the argument 0 this is exactly `1.0f` for every finite `ω` (`cosf(0) == 1`, `sinf(0) == 0`), and `ω_f = θ^(−2f/256)` with `θ = 1e7` is always finite positive (`:309-312`). The factor is then multiplied into both score terms — `amp * freq_scale_sq[f] * cosf(phase)` and `extra_weight[f] * freq_scale_sq[f] * k_mag` (CPU `:487-492`; GPU `triattention-score.cu:269`, `:284`, `:294`, `:300`) — so it is an identity multiply on both paths.

- **Not (a) "intentionally disabled":** there is no flag, branch, or config field for it, and the code's own comment asserts the opposite of a disable — it claims the position-0 evaluation *captures* frequency-dependent scaling ("for scaled RoPE (YaRN etc.) ... If we later support YaRN scaling, this would use the actual scaling factors", `:321-327`). That is a mathematical non-sequitur — a rotation evaluated at position 0 is `cos²+sin²` for *any* frequency — but it is an admission that the function is a **placeholder for future work**, which is (b).
- **Not (c) "active through another symbol":** the documented role is `fscale²_f = 1/ω²` (`src/docs/TRIATTENTION.md:41`), and a grep for `freq_scale` across `src/` returns only the unrelated upstream RoPE `freq_scale` (YaRN scaling in `ggml/` and `common/`) plus TriAttention's own pass-through declarations (`llama-triattention.h:160`, `:271`; `ggml-cuda.h:70-71`; `TRIATTENTION-API.md`). The scorer's only other per-frequency weights, `q_mean_abs` and `extra_weight = E[‖q_f‖] − ‖E[q_f]‖` (`:345-360`), are calibration-derived, not `1/ω²`.
- **The omission is not cosmetic:** had it been implemented, the weight would span `θ^(4f/256)` ≈ `10^13.9` across the band at `f = 127`. `[INFERENCE]` — arithmetic from the documented formula.

## Open questions

- **H1: has the NaN path ever actually run?** The arithmetic is decided from source, but no log or run in the wiki shows the default configuration being executed and scores being printed. One invocation with `--triattention-offset-max 65536` versus the default is enough to observe it (`--triattention-log` at init time prints `Geometric offsets: N`). `[UNVERIFIED]` — nothing was executed here.
- **H1: what should `offset_max = 0` mean?** Two defensible fixes with different blast radius: treat 0 as "a single offset at 1" inside `triattention_build_offsets` (repairs every existing config silently) or reject the configuration and warn in validation ([[ta-7-config-validation]]). The code contains no statement of intent; the shipped default is unintentional relative to both the header comment and the design document.
- **H2: what is the correct inverse for MRoPE?** Inverting qwen35's rotation needs the three section positions (`[11,11,10,0]` over dims `[0,64)`), or a decision to score in a reduced 32-pair basis. The scorer currently has neither the section array nor the corresponding position streams; the paper's own account of MRoPE handling (arXiv 2604.04921) is cited in the sources but not present in the repo. Not decidable from this checkout.
- **H2: is the defect locked in by validation?** The loader enforces `freq_count == head_dim/2` ([[triattention-calibrate]]), which is exactly the wrong invariant for a 64-of-256 rotation — so a corrected profile would be *rejected* by the current loader. Confirm that invariant before proposing a fix.
- **H3: was there ever a branch that computed `1/ω²`?** Not decidable from the working tree — no history is in scope, and the only trace is the placeholder's own "if we later support" comment.
- **Do H2 and [[ta-1-wht-inversion-256]] confound the same measurement?** Both corrupt the recovered key vector before scoring, so no existing eviction-quality number can attribute degradation to either one — the same sequencing problem [[roadmap]] already records for items 1 and 2.
