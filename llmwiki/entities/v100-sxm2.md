# Tesla V100-SXM2-16GB

## What it is

The deployment target the whole project is built around: **Tesla V100-SXM2-16GB** — Volta, compute capability `sm_70`, 900 GB/s HBM2, 16 GB, **no INT tensor cores** — on Ubuntu 22.04 / CUDA 12.4 ([[source-state-md]] preamble).

The last clause is the load-bearing constraint and the reason [[tq-1-missing-gemm-kernels]] matters as much as it does: on this part the only tensor-core arithmetic available is **FP16**, so any quantized path that would otherwise be handed to INT8/INT4 MMA falls back to `__dp4a` byte-wise dot products, to FP16 MMA over freshly dequantized data, or out of the kernel entirely into cuBLAS/MAGMA — with no integer tensor throughput to hide the dequantization. The project's own build script states the same split in its arch legend: `70 == V100, FP16 tensor cores` and `75 == Turing, int8 tensor cores` (`src/ggml/src/ggml-cuda/CMakeLists.txt:13-14`).

## How it works

What `sm_70` does and does not have, read out of the dispatch/arch guards rather than from spec sheets (`src/ggml/src/ggml-cuda/common.cuh`):

| Capability | Gate in code | Available on `sm_70`? |
| :--- | :--- | :--- |
| `__dp4a` byte dot product | `GGML_CUDA_CC_DP4A = 610` (`common.cuh:51`) | yes |
| FP16 MMA | `VOLTA_MMA_AVAILABLE` when `__CUDA_ARCH__ == GGML_CUDA_CC_VOLTA` (`common.cuh:273-276`, `GGML_CUDA_CC_VOLTA = 700` at `:52`) | yes — the one tensor-core path |
| INT8/INT4 MMA | `TURING_MMA_AVAILABLE` from `GGML_CUDA_CC_TURING = 750` (`common.cuh:278-280`, `:53`) | **no** |
| BF16 MMA | `bf16_mma_hardware_available()` requires `cc >= GGML_CUDA_CC_AMPERE = 800` (`common.cuh:322-326`, `:54`) | **no** |
| Async copy / `cp.async` | `cp_async_available()` from `800` (`common.cuh:356-358`) | **no** |
| Flash attention | `FLASH_ATTN_AVAILABLE` unconditional (`common.cuh:294-295`); FP16 FA kernels carry Volta code paths (`src/ggml/src/ggml-cuda/fattn-mma-f16.cuh` mentions `VOLTA`) | yes |

Three consequences that shape every design decision in this repo:

1. **The bf16 fallback is the worst case here.** [[performance-profile]]'s dominant kernel is instantiated `<float, __nv_bfloat16>`. BF16 needs Ampere for hardware acceleration, so on Volta that instantiation is dequantize-plus-cuBLAS with no tensor core to run the multiply on.
2. **The ternary weight type loses its MMA path.** `ggml_cuda_should_use_mmq()` gates `GGML_TYPE_PTQ1_0` on `turing_mma_available(cc)` (`src/ggml/src/ggml-cuda/mmq.cu:366+`, PTQ1_0 case), so on `sm_70` the ternary quant cannot take the MMQ tile path at all. `GGML_TYPE_PQ2_0` is listed unconditionally in the same switch, so the 2-bit weights keep an MMQ path — but the opt-in Hopper wgmma variant for `Q1_0`/`PQ2_0` requires `ggml_cuda_mul_mat_q1_hopper()` and is reachable only on `sm_90` (`src/ggml/src/ggml-cuda/ggml-cuda.cu:1866-1873`).
3. **Types with no kernel land in cuBLAS.** `ggml_cuda_mul_mat()` is a sequence of predicate tests — `mmvf` → `mmf` → `mmvq` → `mmq` → and finally `ggml_cuda_mul_mat_cublas()` (`src/ggml/src/ggml-cuda/ggml-cuda.cu:1876`). TurboQuant's `turbo2_0`/`turbo3_0`/`turbo4_0` appear in neither `ggml_cuda_should_use_mmvq()` (`src/ggml/src/ggml-cuda/mmvq.cu:293`) nor `ggml_cuda_should_use_mmq()` (`src/ggml/src/ggml-cuda/mmq.cu:366`), so they always take that last branch. See [[gemm-dispatch]] and [[tq-1-missing-gemm-kernels]].

## Where it lives

No file describes the hardware; the target is *materialised* in three places inside this repo — the launch scripts, the build arch lists, and the calibration profile — and named in the sources.

### The GPU matrix as published ([[source-readme]], *GPU Compatibility Matrix*)

| Build Folder | Target Architectures | Supported GPUs | Min. NVIDIA Driver |
| :--- | :--- | :--- | :--- |
| **`build/cuda13/`** *(Universal Fat Binary)* | `sm_75`, `sm_80`, `sm_86`, `sm_89`, `sm_90`, `sm_100`, `sm_120` | • **Turing**: GTX 1650/1660, RTX 2060–2080 Ti, T4<br>• **Ampere**: RTX 3050–3090, A10, A40, A100<br>• **Ada Lovelace**: RTX 4060–4090, L4, L40<br>• **Hopper**: H100, H200<br>• **Blackwell**: RTX 50xx, B100, B200 | `>= 550.x` |
| **`build/cuda12.4/`** *(Legacy Release)* | `sm_61`, `sm_70`, `sm_75`, `sm_80`, `sm_86` | • **Pascal**: GTX 1060–1080 Ti, Tesla P40, P100<br>• **Volta**: Titan V, Tesla V100<br>• **Turing**: GTX 16xx, RTX 20xx<br>• **Ampere**: RTX 30xx, A100 | `>= 525.x` |

So per its own documentation, the V100 is served only by the **legacy CUDA 12.4** artifact; the CUDA 13 universal binary starts at `sm_75` and cannot run on Volta.

### Which arch targets the source build actually emits

- `src/CMakePresets.json` — read in full; it contains **no CUDA presets and no `CMAKE_CUDA_ARCHITECTURES`** anywhere (only SYCL, Vulkan and host-compiler presets). The architecture list is therefore whatever the ggml default computes, unless the caller passes `-DCMAKE_CUDA_ARCHITECTURES` explicitly.
- `src/ggml/src/ggml-cuda/CMakeLists.txt:8-56` — the default path. With CUDA < 13 and not `GGML_NATIVE`:
  - `50-virtual 61-virtual 70-virtual` (`:31`),
  - then `75-virtual 80-virtual 86-real` (`:34`),
  - then `89-real 90-virtual` when CUDA ≥ 11.8 (`:37`),
  - then `120a-real` (CUDA ≥ 12.8, `:51`) and `121a-real` (CUDA ≥ 12.9, `:54`).
  The suffix semantics are documented in the same file (`:20-22`): *virtual = PTX only, JIT at first run; real = device code for that arch*. **`sm_70` is emitted as PTX only (`70-virtual`) — the stock build produces no sm_70 SASS**, and with CUDA 13 the `50/61/70` entries are dropped entirely because the whole append is inside `if (CUDAToolkit_VERSION VERSION_LESS "13")`.
- [[source-readme]]'s native-build example instead passes `-DCMAKE_CUDA_ARCHITECTURES="75;80;86;89;90;100;120"` — no `70`. [INFERENCE] Because PTX is only forward-compatible (a `compute_75` module cannot be JIT-compiled *down* to `sm_70`), a build following the README verbatim should produce a binary with no loadable code for the deployment target at all. The README never reconciles this with its own Volta row.

### The shipped artifacts

The published `Release/` layout ([[source-readme]]) does not exist in this tree; instead the repo root carries two prebuilt archives (`build/`, read directly):

| Archive | Size | CUDA library inside | Size |
| :--- | ---: | :--- | ---: |
| `build/cuda124.zip` | 811 787 748 B | `cuda12.4/bin/libggml-cuda.so` | 236 919 936 B |
| `build/cuda13.zip` | 1 663 354 910 B | `cuda13/bin/libggml-cuda.so` | 337 985 192 B |

Both archives are LZMA-compressed (info-zip cannot extract them; the members were decompressed and scanned directly). Scanning the two fat binaries for arch markers gave:

- **CUDA 12.4 library:** the only architecture string present in the whole 237 MB is `sm_86` — 164 embedded PTX modules, each beginning `.version 8.2 / .target sm_86`. No `sm_70`, `sm_75`, `sm_80` or `sm_61` marker was found anywhere.
- **CUDA 13 library:** driver/JIT option markers `-arch sm_75`, `sm_80`, `sm_86`, `sm_89`, `sm_90`, `sm_100`, `sm_120a` (with 38–55 occurrences each) plus 165 `compute_120a` occurrences.

**Whether the shipped CUDA 12.4 library actually contains `sm_70` SASS is `[UNVERIFIED]`.** CUDA cubins carry no `sm_XX` ASCII string, so an absence of markers is not proof of absence; there is no `cuobjdump`/`nvdisasm` on this machine to enumerate the fatbin entries. What can be said is that the artifact the README designates as the *Volta* build is the one whose arch markers I could not find, and that [[benchmarks]] records no V100 run in either source. That combination is worth a direct check (`cuobjdump -lelf`) before any Volta deployment.

## Known issues

- [[tq-1-missing-gemm-kernels]] — **the** Volta issue: with no INT tensor cores, the cuBLAS/MAGMA fallback for the TurboQuant KV types is the recorded 38.81 % (157 ms) of GPU time and cannot be absorbed by integer throughput.
- [[ta-4-cooperative-fwht-race]] — the shared-memory WHT rotation assumes 64 active threads and is documented as undefined behaviour *on Volta specifically* (`tq-1`'s sibling in the same `triattention-score.cu` kernel).
- [[benchmarks]] — every published number is RTX 3090 (Ampere). No V100 measurement exists, so the compression targets and the 1.39× are unvalidated on the actual target.
- [[ta-3-cpu-fallback-transfers]] — the CPU fallback's per-cell synchronous D2H copies hit the PCIe host link, not HBM2; the 900 GB/s headline is irrelevant to that path.
- Build coverage: README's native build recipe omits `sm_70` while the stock CMake default emits it as PTX only — see *Where it lives* above.
