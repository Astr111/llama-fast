# Git & Environment Conventions

## Commits (Conventional Commits 1.0.0)

**Format:** `<type>[optional scope]: <description>`
**Language:** English

| Type       | When to use                                               |
| :--------- | :-------------------------------------------------------- |
| `feat`     | A new feature (role, service, template, component)        |
| `fix`      | A bug fix in code, configuration, or a template           |
| `refactor` | A code change that neither fixes a bug nor adds a feature |
| `ci`       | Changes to `.gitlab-ci.yml` or CI scripts                 |
| `docs`     | Documentation-only changes (`README.md`, `AGENTS.md`)     |
| `chore`    | Routine tasks (dependency updates, `.gitkeep`)            |

**Scope Examples:**

- `feat(psono): add password manager role`
- `fix(plane): correct proxy port binding`
- `ci(pipeline): migrate pip to uv`
- `docs(readme): update CI variables section`

## Branches (Conventional Branch 1.0.0)

**Format:** `<type>/<description>`

| Prefix     | Purpose                           |
| :--------- | :-------------------------------- |
| `feat/`    | New feature                       |
| `fix/`     | Bug fixes                         |
| `hotfix/`  | Urgent production fixes           |
| `chore/`   | Routine tasks, dependency updates |
| `release/` | Release preparation               |

**Rules:**

- Only lowercase letters `a-z`, numbers `0-9`, hyphens `-`, and dots `.`.
- Underscores `_` and spaces are **PROHIBITED**.
- Hyphens and dots cannot be consecutive, leading, or trailing.
- **Main branch:** `main`

**Examples:**

- `feat/add-psono-role`
- `fix/plane-proxy-port`
- `hotfix/security-patch`
- `chore/update-ansible-collections`
- `release/v1.2.0`

## BMad Delivery Pipeline (required for multi-step feature work)

Planned work runs through one fixed pipeline. Do not substitute an improvised flow.

$$\text{bmad-architecture} \;\rightarrow\; \text{bmad-ticket (epics)} \;\rightarrow\; \text{bmad-ticket (stories, per epic)} \;\rightarrow\; \text{parallel subagents, one per epic} \;\rightarrow\; \text{bmad-build-auto per ticket}$$

### Toolchain and fixed paths

| Thing | Value |
| :--- | :--- |
| Runner | `uv` — every BMad script is invoked as `uv run --no-cache …` |
| Runtime | `_bmad/` at `{project-root}`; scripts byte-copied from `.agents/skills/` by `bmad setup` |
| Skills | `.agents/skills/<skill>/SKILL.md` — read by path; harnesses outside Amp/Claude/Codex do **not** auto-register them |
| `{output_folder}` | `_bmad-output/` (from `_bmad/config.toml`) |
| Tickets | `_bmad/method/scripts/tickets.py` |
| Renderer | `_bmad/scripts/render_skill.py` |
| Memlog | `_bmad/scripts/memlog.py` |
| Config | `_bmad/scripts/resolve_config.py`, `resolve_customization.py` |

`{project-root}` is this directory (nearest ancestor holding `_bmad/`). Never `cd` during a skill run; pass `--project-root "$PWD"`.

### Stage 0 — preconditions (check before every run)

1. `uv run --no-cache _bmad/scripts/resolve_config.py --project-root "$PWD" --key core.output_folder --key modules.bmm.active_initiative` — must return an `output_folder`, and the active initiative when work is already scoped.
2. Set or change the initiative by editing `[modules.bmm]` `active_initiative = "<folder-name>"` in `_bmad/custom/config.user.toml`. `output_folder` defaults to `{project-root}/_bmad-output`; the initiative folder is `{output_folder}/<initiative>/`.
3. **Clean working tree is mandatory.** `bmad-build-auto` HALTs with `version-control metadata not writable` on a dirty tree. The BMad scaffolding (`_bmad/`, `.agents/`, `.claude/`, `skills-lock.json`, `AGENTS.md`) and the ticket tree under `_bmad-output/` are the git-backed ticket store: commit them. Build-only noise goes into `.gitignore`: `src/build-x64-linux-gcc-debug/`, `.omp/`, `.vscode/`, and `_bmad/render/` (per-run hashed workflow snapshots, regenerated by every `render_skill.py` call).
4. `npx skills update` invalidates `_bmad/`; re-run `bmad setup` afterwards.

### Stage 1 — Architecture (`bmad-architecture`)

Produces one architecture **spine** per initiative (epic altitude when the initiative spine already exists and leaves the epic's invariants open). Read `.agents/skills/bmad-architecture/SKILL.md` first; when a spec/PRD exists, fold the spine into it as a companion.

- Input is a spec package, a PRD, a raw idea, or this brownfield codebase. For this repo: investigate `src/`, `ggml/`, and `state.md` before deciding — ratify existing conventions, never invent a parallel one.
- Writes go only through the memlog; the spine is distilled from it at the end:
  `uv run --no-cache _bmad/scripts/memlog.py init --workspace _bmad-output/architecture-<slug> --field scope=… --field purpose=… --field altitude=…`
  `uv run --no-cache _bmad/scripts/memlog.py append --workspace … --type <decision|constraint|version|assumption|question|direction|event> --text "…"`
- Output: `_bmad-output/architecture-<slug>/architecture-<slug>.md`, frontmatter `status: final`.
- Reviewer gate before handoff: `uv run --no-cache .agents/skills/bmad-architecture/scripts/lint_spine.py --workspace _bmad-output/architecture-<slug>` plus every `workflow.finalize_reviewers` lens as a parallel subagent.
- Headless runs follow `.agents/skills/bmad-architecture/references/headless.md` and return the `status`/`spine`/`open_questions` JSON. Run headless when dispatched as a subagent (record inferences as `assumptions[]`, gaps as `open_questions[]`, never invent).

### Stage 2 — Epics, then stories (`bmad-ticket`)

`bmad-ticket` owns both levels; there is no separate epics skill.

1. **Initiative → epics.** Envelope the initiative (`initiative-template.md`), hold the source's lines as stable ids, then write one `[[epic]]` table per epic into `_bmad-output/<initiative>/tickets.toml` in build order (`assets/tickets-template.toml`). Each epic gets `_bmad-output/<initiative>/epic-<slug>/epic-<slug>.md`. Cross-epic contracts belong in the spine (Stage 1) and are cited in each adopting epic's References.
2. **Epic → stories (inception).** Per epic, one `[[entry]]` table per story in `_bmad-output/<initiative>/epic-<slug>/tickets.toml`. Table order is build order; `after` is prerequisites only. Because the build runs unattended, entries must carry `verify` and the design unknowns already settled (`unknown`, `refine`, `plan_checkpoint`, `done_checkpoint`).
3. Verify with `uv run --no-cache _bmad/method/scripts/tickets.py --project-root "$PWD" status <initiative folder>` → then `… next`: `ready_to_start` respects `after`; `blocked` must be empty before fan-out. Leaf files appear only after `tickets.py pull <epic folder> <id>`.

### Stage 3 — parallel epic execution (one subagent per epic)

Fan out with the `task` tool: **one subagent per epic, launched in a single message, all blocking, all awaited together.** Never background or detach a builder — an unattended build has no event loop to resume it (this is also `bmad-build-auto`'s own rule).

Per epic subagent:

1. Work in an **isolated `git worktree` on its own branch**, never in the shared working tree:
   `git worktree add "<project-root>-wt/<epic-slug>" -b feat/<epic-slug> main`
   Parallel builders in one tree corrupt each other and every one of them fails the clean-tree check. Worktrees live as siblings of the project root — none inside it, or they show up as untracked and dirty the tree.
2. Loop the epic's `tickets.toml` entries in table order, respecting `after`, one ticket per `bmad-build-auto` invocation:
   ```
   uv run --no-cache _bmad/scripts/render_skill.py --project-root "$PWD" --skill "$PWD/.agents/skills/bmad-build-auto"
   ```
   then read and follow the absolute `workflow.md` path it prints. Route/review overrides, when the epic needs them: `--set workflow.route=oneshot|full`, `--set workflow.review=none|quick|thorough`.
3. `bmad-build-auto` handles exactly one ticket per invocation and must not be pointed at another. Repeat until `tickets.py next <epic folder>` reports no `ready_to_start` and no `in_progress`.
4. Leave `done` alone — it is the orchestrator's, set with `tickets.py mark <epic folder> <ref> done`. A HALT sets `blocked` with a blocking condition; report it up rather than clearing it.
5. Run no build/lint/test/formatter sweeps mid-flight inside the loop; `bmad-build-auto` runs its own verification per ticket.

**Fan-out gate:** only epics whose touch points are disjoint may run concurrently (Stage 2 must have drawn non-colliding lanes); an epic with `after` naming another epic's entry starts only after that provider is built. Cap concurrency at 32 subagents; extra epics queue.

**Integration:** merge epic branches back in the initiative's `tickets.toml` order — one integration owner, cherry-pick or merge sequentially, resolve conflicts there, and only then mark tickets `done`. A completed epic reverts to `bmad-retrospective`.

## LLM Wiki (`llmwiki/`)

This repo maintains a persistent, LLM-written wiki between the raw sources and the code. Read `llmwiki/SCHEMA.md` **before** any wiki operation — ingest, query, or lint. It carries the page templates, the frontmatter contract, and the procedures; this section carries only the invariants.

- **Layers.** `llmwiki/raw/` is immutable — read it, never write it. `llmwiki/{sources,entities,concepts,issues,topics}/` is LLM-owned. `AGENTS.md` + `llmwiki/SCHEMA.md` are the schema; co-evolve them with the user.
- **Start navigation at `llmwiki/index.md`.** It is the catalog; drill into pages from there. `llmwiki/log.md` is the append-only history — `grep "^## \[" llmwiki/log.md | tail -5` for recent operations.
- **One source is filed, not indexed.** Ingesting means: snapshot into `raw/` with a recorded sha256, write a `sources/` page, update every entity/concept/issue/topic page it touches, update `index.md`, append to `log.md`. A source typically touches 10-15 pages.
- **Cite or mark it.** Prose claims cite `([[source-*]])`; code claims cite `path:line` and the path goes into the page's `verified:` frontmatter. Anything read only from prose is unverified; anything unreadable is marked `[UNVERIFIED]` inline, never dropped.
- **Contradictions are data.** Never overwrite an older claim silently — annotate both sources and log it.
- **Answers compound.** A synthesis produced in chat that the user would want again is filed back as a `topics/` page and logged; chat history is not a store.
- **Lint after writing.** Orphan pages, broken `[[links]]`, stale source hashes, and missing pages behind dangling links are defects to fix, not observations to report.
- The wiki is a git repo of markdown: it is committed and reviewed like code, and it is the intended Obsidian vault (`llmwiki/` as the vault root).
